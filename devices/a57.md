# OPPO A57 (a57) — what the recovery needs beyond the packing

Written after bringing the A57 recovery up on the phone's own 4.19 kernel.
Everything here is hardware fact gathered from the phone, not a guess.

## The display

`arch/arm64/boot/dts` leaves `/soc/qcom,mdss_mdp@1a00000/qcom,mdss_dsi@0`'s
`clocks` property pointing `ext_byte0`, `ext_byte1`, `ext_pixel0` and
`ext_pixel1` at the two `qcom,mdss_dsi_pll` nodes (`phandle` 0x5e/0x5f)
instead of the `qcom,clock_gcc-mdss@1800000` wrapper (`phandle` 0x59).

`dsi_link_hs_clk_set_rate()` then answers `-EINVAL` and the panel stays dark
the first time anything blanks it — the recovery's own screen-off, for one.
The clock names and the wrapper are identical between the 4.9 and 4.19 trees,
so the four entries are replaced with the wrapper's phandle and the GCC
indices the 4.9 TWRP for this phone uses:

| property | phandle | index |
| --- | --- | --- |
| `ext_byte0_clk` | 89 | `0xfb32f31e` |
| `ext_byte1_clk` | 89 | `0x585ef6d4` |
| `ext_pixel0_clk` | 89 | `0x087c1612` |
| `ext_pixel1_clk` | 89 | `0x8067c5a3` |

With that, `gcc_mdss_byte0_clk` reads back exactly `64255500` and the panel
comes up.

The panel node
`qcom,mdss_dsi_oppo16061boe_nt35521s_b8_720p_video` also has no `mi,*`
brightness maxima, which the UI reads out of the device tree; the four
properties it asks for are added with the value of
`qcom,mdss-dsi-bl-max-level` (255).

## The device tree the UI reads

The phone's kernel is fbdev (`# CONFIG_DRM is not set`), so
`/sys/module/msm_drm/parameters/dsi_display0` does not exist. The panel's
name is given to the recovery in `skyward/device.toml`'s stead instead.

## The services

The keymaster on this phone is HIDL `@3.0`, reached over `/dev/hwbinder`,
and it needs the whole Qualcomm stack beside it:

- `hwservicemanager` and `vndservicemanager`, neither of which a recovery's
  own tree carries
- `qseecomd`, which registers the listeners the secure world calls back
  through (`vendor.sys.listeners.registered`)
- `libvndksupport.so`, which `/vendor/lib64/libhardware.so` needs and which
  only the installed system carries

The programs and their dependency closure travel inside the recovery, so a
formatted `system` or `vendor` does not take the key service with it.

## SELinux

The loop worker reads the APEX bundles through the file descriptor the
recovery opened, and the policy does not let `u:r:kernel:s0` use a
descriptor of `u:r:recovery:s0`: every read comes back `EIO` and no bundle
mounts. The image's command line carries `androidboot.selinux=permissive`.

## A bundle whose payload is not erofs

`apex_payload.img` inside this phone's bundles is ext4. Asking the kernel to
mount it as erofs answers `EIO`, which `mount_ro()` took as the end of the
search rather than a refusal, so `com.android.runtime` never opened.

## Where it stands

Working: display, touch, the volume and power keys, and the panel's own back
key (read from the panel's stream, which `scan()` had taken in as the panel
and therefore kept out of `buttons`).

Not working yet: opening the data partition. The `IServiceManager::get` call
Skyward makes to `hwservicemanager` used to come back with `TF_STATUS_CODE`
`-22`: the interface name was padded to a word before the method's own
arguments were read, so every argument after it was a byte out. That is
fixed. Where opening the partition stops now is what the logs below are for.

## What to read after flashing

Two sets of lines go to the kernel log, and neither costs anything when the
pages are not moving:

- `decrypt: ...`, one line per thing opening the partition does: the table's
  entries and the device, whether the partition is encrypted whole, how many
  bytes the key service gave back, the mapping, the mount, the shared key and
  the name it got, each user, the protector's blob and what it is bound to,
  the weaver's slot, the gatekeeper note, the keystore blob and the inner one
  it holds, the CE key, `/sdcard`. Where it stopped is the last line printed.
- `N frames in M ms: ...`, every two seconds while frames are going out: what
  a frame costs to draw, what it costs to put on the panel, the worst, and how
  many came late. A page that feels slow is one whose frames are late here.

`skyward decrypt` says the same to a terminal, in order, and
`skyward decrypt --credential <what the owner types> --user 0` goes on to open
that user's own files with it; `--clean` takes the partition back down after.

## /metadata

The phone's own table calls the metadata partition `reserve2`; it is ext4,
16 MiB, and holds the installed system's aconfig, apex and bootstat folders.
Skyward reaches it as `/dev/block/by-name/metadata`, which nothing on this
phone creates, so the settings the pages keep were never read or written.

The recovery's init makes the name:

`
symlink /dev/block/bootdevice/by-name/reserve2 /dev/block/by-name/metadata
`

`mount_ro()` then finds it as ext4 and the settings are kept.
